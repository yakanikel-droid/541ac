# Героические копии классических подземелий

Технический отчёт и шпаргалка для AzerothCore 3.3.5a.

Проект: [yakanikel-droid/541ac](https://github.com/yakanikel-droid/541ac)

## 1. Результат работы

Для 19 классических подземелий созданы отдельные героические копии с Map ID `1000–1018`.

Итоговое поведение соответствует WotLK:

- рядом с мини-картой выбирается обычная или героическая сложность;
- отдельный второй портал рядом с обычным входом не создаётся;
- обычный синий портал остаётся на месте;
- в героическом режиме на портале появляется оригинальный фиолетовый череп WotLK;
- при возврате в обычный режим череп исчезает;
- визуал обновляется сразу после смены сложности, без необходимости двигать персонажа;
- вход направляет в обычную карту при Normal и в копию `1000–1018` при Heroic;
- у обычной и героической версии разные Map ID, поэтому создаются отдельные сохранения инстансов;
- внутренние порталы выхода работают в героических копиях;
- устранён мгновенный выброс из Крепости Тёмного Клыка, Пика Чёрной горы и Пещер Стенаний;
- проверено в клиенте и на сервере — итоговый вариант работает.

На текущем этапе существа в героические карты ещё не скопированы. Отдельные характеристики существ и героический лут также пока не созданы.

## 3. Почему используются отдельные Map ID

Обычный Heroic Difficulty на том же Map ID не даёт полной независимости, необходимой для этой реализации. Отдельные карты `1000–1018` обеспечивают:

- отдельный `instanceId`;
- отдельное сохранение прохождения;
- независимый сброс;
- возможность в дальнейшем создать отдельные спавны существ;
- возможность назначить отдельные шаблоны существ и отдельный лут;
- отсутствие смешивания обычного и героического прогресса.

Название карты не дополнялось строкой «(героическая)». Режим обозначается стандартной иконкой сложности возле мини-карты и черепом на входном портале.

## 4. Серверные файлы геометрии

Для каждого нового Map ID были созданы копии файлов исходной карты.

### 4.1 MMaps

Копируются:

- корневой файл `XXX.mmap` → `YYYY.mmap`;
- все тайлы `XXX*.mmtile` → `YYYY*.mmtile`;
- изменяется только префикс Map ID, координаты тайла сохраняются.

Итог копирования:

- MMaps: `19 из 19`;
- MMTiles: `187`;
- ошибок: `0`.

### 4.2 Maps

Копируются все существующие файлы `XXX*.map` с заменой исходного Map ID на новый.

Итог:

- скопировано `184` map-тайла;
- для части подземелий отдельных `.map`-тайлов в исходной выгрузке не было.

Отсутствие `.map`-тайлов не всегда является ошибкой: некоторые классические подземелья построены преимущественно на WMO и не имеют набора обычных terrain-тайлов. Нельзя создавать пустые вымышленные `.map`-файлы.

### 4.3 VMaps

Копируются:

- `XXX.vmtree` → `YYYY.vmtree`;
- существующие `XXX_*.vmtile` → `YYYY_*.vmtile`.

Итог:

- VMTrees: `19 из 19`;
- VMTiles: `89`;
- ошибок: `0`.

Предупреждение «vmtree copied, but no vmtile files found» допустимо, если исходная карта действительно состоит только из дерева VMap без отдельных тайлов.

### 4.4 Размещение на сервере

Готовые файлы должны находиться непосредственно в рабочих каталогах сервера:

```text
/home/kanika/Azerothcore/server/data/maps
/home/kanika/Azerothcore/server/data/vmaps
/home/kanika/Azerothcore/server/data/mmaps
```

Не нужно оставлять их во вложенных временных каталогах `heroic_maps`, `heroic_vmaps` или `heroic_mmaps`, если конфигурация сервера не указывает на эти каталоги отдельно.

## 5. DBC

Используются три изменённых DBC:

```text
DBFilesClient\Map.dbc
DBFilesClient\MapDifficulty.dbc
DBFilesClient\AreaTrigger.dbc
```

### Map.dbc

Добавлены записи карт `1000–1018`, созданные на основе исходных классических подземелий.

Ключевые требования:

- новый уникальный Map ID;
- тип карты — подземелье;
- корректные имя, каталог карты и параметры инстанса;
- сервер и клиент должны использовать одинаковую версию файла.

Физический каталог карты остаётся основанным на исходной карте. Новые Map ID используют скопированные серверные `maps/vmaps/mmaps`.

### MapDifficulty.dbc

Добавлены записи сложности для карт `1000–1018`. Они позволяют клиенту и серверу распознавать новые карты как героические инстансы и показывать стандартную иконку героического режима возле мини-карты.

### AreaTrigger.dbc

Для выходов героических копий добавлены AreaTrigger ID `5873–5965`.

Всего зарезервировано 93 новых ID. Их положение скопировано с соответствующих AreaTrigger исходных карт, но поле Map ID заменено на `1000–1018`.

### Установка DBC

На сервере:

```text
/home/kanika/Azerothcore/server/data/dbc/Map.dbc
/home/kanika/Azerothcore/server/data/dbc/MapDifficulty.dbc
/home/kanika/Azerothcore/server/data/dbc/AreaTrigger.dbc
```

В клиентском MPQ-патче:

```text
DBFilesClient\Map.dbc
DBFilesClient\MapDifficulty.dbc
DBFilesClient\AreaTrigger.dbc
```

После изменения клиентских DBC необходимо удалить каталог `Cache` клиента и полностью перезапустить игру.

## 6. SQL

### 6.1 instance_template

Для карт `1000–1018` создаются отдельные записи `instance_template` путём копирования параметров исходных карт:

- `parent`;
- `script`;
- `allowMount`.

Это позволяет копиям использовать существующие instance scripts. Позже скрипты отдельных подземелий необходимо проверить с учётом нового Map ID: жёсткие сравнения с исходным Map ID могут потребовать доработки.

### 6.2 AreaTrigger выходов

Файл:

```text
heroic_areatrigger_teleports.sql
```

Он выполняет следующие операции:

1. связывает исходные AreaTrigger с новыми ID `5873–5965`;
2. копирует геометрию в таблицу `areatrigger`;
3. назначает новый Map ID `1000–1018`;
4. копирует назначения выхода в `areatrigger_teleport`;
5. копирует `areatrigger_scripts`, только когда они действительно нужны.

Если сервер пишет:

```text
Area trigger (ID:xxxx) does not exist in AreaTrigger.dbc
```

это означает, что сервер загрузил старый `AreaTrigger.dbc`, файл установлен не в тот `DataDir` либо worldserver не был полностью перезапущен.

Если сервер пишет:

```text
AreaTrigger entry (...) has SmartTrigger enabled but no SmartAI entries
```

нужно проверить `areatrigger_scripts`. Нельзя назначать `SmartTrigger` новой записи без соответствующей строки `smart_scripts`.

### 6.3 Визуальные черепа

Финальный файл:

```text
heroic_classic_skulls_all.sql
```

В нём созданы 29 GameObject:

- template/entry `990030–990058`;
- `type = 5` — Generic;
- `displayId = 7149`;
- `ScriptName = go_heroic_classic_skull`;
- отдельные координаты, поворот и размер для каждого входа.

`displayId 7149` — штатная модель клиента 3.3.5a:

```text
World\Generic\ActiveDoodads\InstancePortal\InstancePortal_PurpleDifficultyIcon.mdx
```

Новая модель или новый `GameObjectDisplayInfo.dbc` для черепа не требуются.

Координаты черепов вычислены из реальных размещений `InstancePortal.mdx` в ADT/WMO, а не из приблизительных координат телепорта.

Важно: координаты основания модели черепа нельзя использовать как безопасную ГМ-точку `.go xyz`. Основание модели иногда находится ниже поверхности, внутри WMO или над перепадом высоты.

## 7. Изменения ядра

Итоговое решение затрагивает следующие файлы AzerothCore.

### `src/server/game/Handlers/MiscHandler.cpp`

В обработке AreaTrigger:

- читается исходный `target_map`;
- при выбранном Heroic исходный Map ID преобразуется в `1000–1018`;
- нормальный режим продолжает использовать исходную карту;
- сохраняются оригинальные безопасные координаты появления внутри подземелья.

В обработке смены сложности:

- после успешного изменения Dungeon Difficulty вызывается отложенное обновление видимости;
- череп появляется или исчезает сразу;
- окно выбора сложности не зависает из-за синхронного полного сканирования объектов.

### `src/server/game/Entities/Player/PlayerMisc.cpp`

После отправки `SMSG_SET_DUNGEON_DIFFICULTY` ставится запрос на обновление видимости объектов:

```cpp
if (IsInWorld())
    UpdateObjectVisibility(true);
```

Это обслуживает групповые изменения сложности.

### `src/server/scripts/World/go_scripts.cpp`

Добавлен скрипт:

```cpp
go_heroic_classic_skull
```

Его `CanBeSeen` возвращает `true` только при:

```cpp
player->GetDungeonDifficulty() == DUNGEON_DIFFICULTY_HEROIC
```

Скрипт зарегистрирован в `AddSC_go_scripts()`.

### `src/server/game/Entities/Player/Player.cpp`

Проверка `IsInAreaTriggerRadius` расширена для героических копий. При проверке новой карты сервер может сопоставить её с исходным Map ID.

Это необходимо, потому что геометрия копии идентична исходной карте, а AreaTrigger были созданы путём копирования исходных координат.

### `src/server/game/Handlers/MovementHandler.cpp`

Клиент 3.3.5a не всегда отправляет `CMSG_AREATRIGGER` для созданных вручную AreaTrigger на новых Map ID. Поэтому сервер дополнительно проверяет ID `5873–5965` после пакетов движения игрока на картах `1000–1018`.

Финальная защита от мгновенного выхода работает так:

1. после входа сервер находит ближайшие выходные триггеры;
2. временно блокирует их для вошедшего игрока;
3. блокировка сохраняется, пока игрок не отойдёт от объёма триггера минимум на 5 метров;
4. после этого выход снова становится активным;
5. когда игрок позже возвращается к порталу, телепорт наружу работает штатно.

Эта логика исправила:

- Map `1008` — Крепость Тёмного Клыка;
- Map `1010` — Пик Чёрной горы;
- Map `1017` — Пещеры Стенаний.

Нельзя снова заменять это решение простым сдвигом координат появления. В Крепости и Пике такой сдвиг помещал персонажа внутрь стен или над пустотой.

## 8. Визуальная часть портала

Финальный вариант:

- исходная синяя модель портала не заменяется;
- ADT не изменяются;
- WMO не изменяются;
- Wow.exe не патчится;
- поверх портала сервер создаёт штатную модель черепа с `displayId 7149`;
- видимость черепа управляется выбранной сложностью.

Также не нужно включать изменённые ADT только ради черепа: череп реализован отдельным GameObject.

## 10. Сборка и установка ядра

Перед заменой файлов рекомендуется сохранить их резервные копии.

После изменения `.cpp` необходимо пересобрать ядро. Используются те же параметры CMake, которыми собирается основной сервер.

Пример полной чистой пересборки:

```bash
cd /home/kanika/Azerothcore/azerothcore-wotlk/build
rm -rf ./*

cmake .. \
  -DCMAKE_INSTALL_PREFIX=/home/kanika/Azerothcore/server \
  -DCMAKE_BUILD_TYPE=RelWithDebInfo

make -j$(nproc)
make install
```

Если на сервере используются дополнительные параметры модулей, скриптов или инструментов, их необходимо добавить к команде CMake. Не следует слепо заменять рабочую команду конфигурации сокращённым примером.

Полная очистка `build` нужна при замене файлов ядра или изменении конфигурации CMake. Для одного SQL, DBC либо `maps/vmaps/mmaps` пересборка ядра не требуется.

После установки:

```bash
sudo supervisorctl restart azerothcore-worldserver
```

Имя процесса Supervisor может отличаться. На текущей установке логи проверялись через процесс `azerothcore-worldserver`.

## 12. Проверка после установки

Для каждого входа выполнить следующий тест:

1. выйти из любого подземелья;
2. установить Normal;
3. убедиться, что череп отсутствует;
4. войти и проверить исходный Map ID;
5. выйти;
6. установить Heroic;
7. убедиться, что череп появился без движения персонажа;
8. войти и проверить Map ID `1000–1018`;
9. убедиться, что персонаж появился на корректной поверхности;
10. отойти от внутреннего портала;
11. вернуться к нему и проверить выход;
12. проверить отдельное сохранение обычной и героической версий;
13. повторить тест группой и одиночным персонажем.

Полезные команды:

```text
.gps
.debug areatrigger
```

При проверке `.debug areatrigger` следует учитывать: клиент может не отправлять событие для кастомного AreaTrigger. Именно поэтому добавлена серверная проверка в `MovementHandler.cpp`.

## 13. Диагностика типичных проблем

### Череп появляется только после движения

Проверить изменения в:

```text
PlayerMisc.cpp
MiscHandler.cpp
```

Нужен отложенный `UpdateObjectVisibility(true)` после групповой и одиночной смены сложности.

### Окно выбора сложности долго закрывается

Нельзя выполнять тяжёлое синхронное обновление сетки прямо внутри opcode handler. Используется отложенное обновление видимости.

### Войти можно, выйти нельзя

Проверить:

- наличие новых записей `5873–5965` в серверном `AreaTrigger.dbc`;
- строки `areatrigger` и `areatrigger_teleport`;
- актуальный `MovementHandler.cpp`;
- полный перезапуск worldserver.

### После входа сразу выбрасывает наружу

Проверить, что установлен `heroic_entry_trigger_fix_v2_541ac.zip`, а не устаревший пакет со сдвигом координат.

### Персонаж появляется в текстуре или падает

Проверить `MiscHandler.cpp`: должны использоваться оригинальные координаты `at->target_X/Y/Z/Orientation`. Нельзя подменять их приблизительными координатами, рассчитанными по направлению взгляда.

### На сервере нет мобов

Это ожидаемо на текущем этапе. Файлы карты содержат геометрию, но не спавны существ. Спавны хранятся в SQL-таблицах world database.

### Сообщения Wrong race mask

Сообщения вида:

```text
Wrong race mask 524288 in playercreateinfo_skills table
```

не относятся к героическим подземельям. Это отдельная работа с кастомными расами и допустимыми масками ядра.

## 15. Резервирование диапазонов ID

Уже используются:

| Диапазон | Назначение |
|---|---|
| `1000–1018` | Heroic Map ID |
| `5873–5965` | AreaTrigger DBC/SQL |
| `990030–990058` | GameObject черепов |

Перед созданием существ и лута необходимо выбрать и зафиксировать новые непересекающиеся диапазоны:

- `creature_template.entry`;
- GUID/ID строк `creature` согласно схеме текущей базы;
- `creature_loot_template.Entry`;
- кастомные предметы, если они понадобятся;
- дополнительные GameObject и скриптовые ID.

Диапазоны нужно записать в этот документ до начала массового копирования.

## 16. Критически важные правила

1. Серверные и клиентские DBC должны совпадать.
2. Нельзя использовать координаты модели черепа для `.go xyz`.
3. Нельзя вручную сдвигать внутренние точки входа без проверки геометрии карты.
4. Нельзя возвращать глобальную замену синего портала фиолетовой моделью.
5. Нельзя назначать `SmartTrigger` без соответствующего SmartAI.
6. Нельзя создавать пустые `.map` или `.vmtile`, если их не было у исходной карты.
7. Обычные и героические существа должны иметь разные template IDs.
8. Обычный и героический лут должны быть независимыми.
9. После изменения C++ нужна пересборка; после SQL/DBC — только корректная установка и перезапуск.
10. Перед массовым изменением базы обязателен резервный дамп.
